Phones either open the database themselves, or post to this server.

What is the difference?
Straight to the database means every participant's phone must reach MySQL on port 3306 from whatever network they happen to be on, for the length of the study. Fewer moving parts, but a phone that cannot open 3306 does not fail loudly — it collects data it never delivers, and the gap shows up in the coverage grid weeks later. The database has to sit somewhere you can deliberately expose.

Through the server means phones post over HTTPS, which nearly every network allows, and carry no database credential at all — so the database can stay private, remote, or managed by someone else. Android gets its own micro-server instance, and a write from a device the study log never recorded joining is refused there and reported.

iPhones always go through the server: an iPhone has no direct-database client, so it is not a choice this study makes.

Changing this later means every enrolled participant has to join again. It is not a setting that can be pushed to a phone: the study address a device joined with is how it identifies the study it belongs to, so it cannot be moved underneath them. Their phones keep collecting but stop delivering until each one re-joins from a new link or QR code. Choose now if you can; changing it mid-study is a decision about contacting every participant.

Either way, setup checks the database answers and that this study can write to it.

What is the difference?
On this machine needs nothing to exist beforehand: the deployment brings up its own MySQL, creates the schema and manages the accounts.

Somewhere I name starts no database of its own — no container, no published port, and none of the services waiting on it. It is offered only when Android phones go through the server above: on the direct path every participant's phone would have to reach that host on its database port from whatever network they are on, which is not something an institution opens up.

Either way, setup checks that the database answers and that this study can write a row to it before enrolment. If your account cannot create the schema or the accounts, the exact SQL is printed for whoever administers the server.

Every participant's phone will open this database directly. The host you name has to accept connections from any network, for the length of the study. An institution will rarely open a database that way — if this is not a server you run yourself, send the data through the server instead.

No participant database password is needed on this path. Phones post to the server and are never given database credentials, so there is nothing for a participant to type and nothing in the published config to read. The server holds its own account, settled at deployment.

The account a phone opens the database with on this path. Participants type it when joining if the study config is served without it. A random one is filled in for you — reveal it with the eye, or type your own.

Connect to this database over TLS

Encrypts everything between this study and the database it names

When would I turn this off?
Only when the server cannot offer it. Most databases can: MySQL 5.7 and later generate a certificate the first time they start, and managed databases require encryption outright. The ones that cannot are a MySQL built without TLS support, a MariaDB older than 11.4 that was never given a certificate, or a host whose administrator has switched it off.

Leave it on if you are not sure. Setup opens the connection and tells you what happened before the study is deployed, so a server that cannot encrypt is reported here rather than found later as a study that enrols and collects nothing.

A database this deployment runs itself is always encrypted and never asks — this question exists because a server you name is one this deployment does not administer.

The study's data will cross the network in clear text. Everything written to this database, and the account password used to write it, can be read by anyone positioned on the network in between. Choose this only for a server that genuinely cannot encrypt.

Encryption keeps the traffic unreadable; it cannot say which server answered. This is what closes that — paste the authority that signed your database's certificate and setup verifies the server against it before deploying. Managed databases publish it (Google Cloud SQL under Connections → Security, DigitalOcean and Aiven behind a Download CA certificate button, RDS and Azure as a documentation download); a server your institution runs has an administrator who can send it; a MySQL that generated its own keeps it as ca.pem in its data directory.

Paste the whole file including the BEGIN and END lines — a bundle holding several certificates can be pasted as it is. Leave it empty to connect encrypted without verifying the server, which you can supply later in the Configurator.

Enable HTTPS

Encrypts everything between participants' phones and this server

I don't have certificate files yet
You need two files: a certificate and its private key. They are free and take a few minutes.

If this machine has a public domain name, install Certbot and run sudo certbot certonly --standalone -d your-domain.example. It writes both files under /etc/letsencrypt/live/your-domain.example/ — fullchain.pem is the certificate and privkey.pem is the key. Paste those two paths below. Certificates last 90 days and Certbot renews them on its own.

If this machine has no domain name — only a local IP like the one above — no authority can issue a certificate for it. Leave HTTPS off. Participants' phones on your own network still reach the study, and the data still goes into the database; what travels unencrypted is the traffic between the phone and this machine.

Full instructions, including the Docker-specific details, are in the project README under SSL certificate.
